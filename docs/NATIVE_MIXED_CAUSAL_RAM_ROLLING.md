# Four-event causal RAM rolling profile

The implemented addition is an opt-in ordinary-RAM software profile: exactly TRIGGER16 → CONTROL16 → CONTROL16 → STOP16 at the original absolute frames960/1920/2880/3840. It composes the genuine song producer, sampler factory, typed controller and causal core. It does not enable frontend PLAY or arbitrary rolling songs.

The existing default pair, after-first CONTROL-only and three-event finite constructors remain separate capabilities. The rolling provider uses `pt_private_mixed_causal_ram_init_rolling` and `pt_private_mixed_causal_ram_rolling_api`; the older CONTROL and finite getters refuse rolling-mode storage. Complete fresh zeroed, noncopyable owner/wrapper/adapter storage and its borrowed inputs remain live until positive terminal source quiet and disposal. The caller excludes concurrent task entries, dispatch and input edits.

## Fixed schedule and ownership

The producer audits all four boundaries, completes take-once replay and checks EOF before preparing resources. It retains the original sixteen reader keys, sample geometry and absolute frame/window bounds. No immediate fallback, moved deadline, measured-jitter allowance or second trigger is introduced.

The RAM provider has only two live command rows. C3 may reuse retired C1 storage and C4 may reuse retired C2 storage. Each reuse requires actual successful core command service with cancel0 and detach, independent positive ticket quiet, no remaining held or findable old command, genuine NULL-handle consumption, and factory/controller disposal. Completion, a numeric command count or quiet from one layer cannot stand in for the other layers' proof. A recycled row receives a fresh serial; an old reference cannot identify its successor.

The provider copies the actual root TRIGGER and latest CONTROL completion histories before reuse. Publication compares their original identities, serials, observed clock/window facts and the complete20-slot expected registry against genuine core history and current state. Disposed command addresses remain opaque numeric identities; later publication does not follow them. Root and latest histories are updated only after genuine committed completion. A forged, mismatched or callback-mutated ownership profile fails closed and retains uncertain ownership.

The rolling-only pre-clock contract applies to both initial TRIGGER publication and later successor publication. It records the authenticated command identity before entering the first external clock callback. If the callback refuses or changes custody before any arm call is entered, the reserved row retains a distinct no-arm tombstone. That record contains the exact owned identity and positive recorded absence of arm entry; it has no live packet, no completed command and no reuse authority. It permits only the matching command's detach/retirement. An empty row, cleared armed bit or raw0 reply cannot substitute for this record.

Actual arm entry has a separate sticky state. Once the arm callback is entered, clearing known/live/armed/quiet fields or the arm-state field during an arm or quiet callback cannot manufacture a no-arm proof. Such changes fail closed, preserve the attempted-arm obligation and require the independent ticket quiet proof. A recorded attempted quiet anchor remains sticky even when the callback clears the rolling profile. On callback mutation, only the actual saved owned command row is restored, preserving genuine prior armed/finished facts together with fault and uncertainty; the provider does not restore the whole port, history or profile. The explicit uncertainty repair is limited to recorded rolling custody, preserving legacy state0 callback semantics. The initial and successor paths retain the same absolute scheduling, publication, history, source and master/cache ownership boundaries. Legacy pair, CONTROL-only and finite paths retain their original contracts; this repair must not extend their admission.

CONTROL updates numeric period/volume or card rate/full uint16 levels on the original sixteen readers. It acquires no new sample masters or cache leases, creates no readers and performs no new upload. Authoritative 16/24-bit masters and the selected Paula/card caches remain owned across both CONTROL events. Numeric card addresses in this RAM profile are numbers; it performs no physical device access.

## STOP, cancellation and quiet

The required final STOP contract closes further rolling command admission while allowing its own already-owned publication to complete at frame3840. The STOP-specific task publication branch and focused negatives are implemented. Its rolling-only initial, successor and quiet custody repairs passed the private ordinary-RAM HOST fixture and all six final-profile regressions. The canonical repository entry has a separate once-only HOST pass; native and device qualification remain separate. It removes musical activity but supplies no command, reader or source quiet proof. Original readers, master pins, cache leases and source storage remain held until their actual independent retirement conditions pass.

Administrative cancellation is separate from musical STOP. Every retained command that names a reader through an action key or any expected registry key needs positive independent ticket quiet before that reader can be released. Expected-only dependencies remain retained after activity is removed. Unknown or reentrant arm replies preserve possible callback ownership; a clean refusal consumes only the once-only attempt allowed by its contract and cannot cause an automatic rearm.

Source shutdown is attempted once after genuine command and reader consumption. Pending or unknown shutdown retains the owner, borrowed source, contexts and sample pins. A later independent read-only source-quiet observation may permit terminal close. There is no forced cleanup, reopen or automatic hardware retry.
