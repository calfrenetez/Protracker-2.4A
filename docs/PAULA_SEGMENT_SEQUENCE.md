# Fixed Paula segment sequence producer

This opt-in HOST producer connects a genuinely measured renderer sequence to
the finite Paula boundary and retained-reader APIs. Its V6 Source is reviewed.
The exact private and standalone canonical 35-case HOST runs each passed once.
Their saved DATA has been independently audited in separate reviews.
The existing sampler and ordinary song lowerers retain their current refusals.
The classic baseline and accepted layout remain outside this addition.

## Finite sequence and exact schedule

The input is an already immutable, validated one-order, one-pattern project
with three genuine current caller pins. A normal silent row precedes the first
SEGMENT. The producer audits and rewinds the same completed renderer owner,
then admits exactly SEGMENT, REPEAT, REPEAT and STOP at origin plus 960, 1920,
2880 and 3840 frames. Plans apply after the preceding returned interval, at
the start of the next interval. It preserves the renderer's geometry and
final CONTROL step/gain, the original dependencies and positive reader key.
It creates no replacement key, fabricated certificate or ownership history.

There are four once-used holders, indexed 0 through 3. Genuine queue command
slots retire independently; this profile adds no fifth command, rolling
holder reuse, row-range traversal or arbitrary song support. The separate
[boundary contract](PAULA_SEGMENT_BOUNDARY.md),
[geometry contract](PAULA_SEGMENT_REPEAT_PLAN.md) and
[retained-reader contract](PAULA_SEGMENT_REPEAT_READERS.md) remain authoritative
for their own admission and lifetime boundaries.

`step` performs local preparation and never publishes. `publish_next` makes
one explicit attempt at the original deadline. Clean pressure preserves the
plan, ticket and deadline for a later explicit call. There is no automatic
retry, clock rebase, catch-up or musical stop-now. A stale revision, late or
malformed sequence, capacity refusal, uncertainty or callback reentry stops
further preparation/publication; retained identities still support cleanup.

## Bounded storage and ownership

The caller supplies a separate ordinary control workspace. Its full capacity
counts against the control budget together with actual child allocation sizes;
the profile bounds captured source spans to 128 and live child allocations
to 16. Known source capacities, selective Chip caches, controls and output
storage must be disjoint. Unknown opaque callback extents remain caller
disjointness obligations. The five original constructor argument/output
spans are guarded during constructor callbacks only and are then erased.
Allocator, configuration and backend metadata are copied byte-for-byte;
callback contexts and source storage must remain live until successful close.

Each later `step` performs one phase operation with work from 1 through 256:
bounded metadata/setup items, timeline ticks/frames, or one existing finite
cache preparation step of at most 256 representation bytes. These units have
different costs. This is no constructor, IRQ latency or native timing promise.

Original current Fast master pins and selective Chip cache leases remain held
through STOP and cancellation. Administrative cancellation may return PENDING.
Release requires genuine independent reader retirement and zero command
references; either proof order is supported. `published_mask` records accepted or uncertain submissions; `detached_mask`
records genuine command service success. `reader_retired` records its separate
genuine reader receipt. None substitutes for ACTIVE, hardware fetch or quiet
proof.
No boundary observation or automatic disposal is inferred. A release callback
fault makes close retain the external owner; already consumed child allocations
remain consumed. A later explicit close can release only the remaining outer
control, without double disposal or child resurrection.

The profile is serialized and noncopyable. It does not protect unannounced
in-place project edits or concurrent callbacks. It does not change current
Fast master, version or selective-cache architecture.
